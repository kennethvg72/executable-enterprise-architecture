# MV-01: Three problems, three passes

Application: rejection-triage
Expected verdict: rejected
Expected rules: DAT-02, INT-05, SIM-01

## The candidate

Support agents get a "contact customer" button. To build it, the candidate sends the email itself, keeps a copy of every customer's taxpayer identifier "for matching later", and adds a cache for the rejection queue. The queue holds at most a few hundred rows, and its page loads in 40 ms today.

```diff
package.json
+    "nodemailer": "6.9.16",
+    "ioredis": "5.4.2",
src/contact.ts
+  const mail = nodemailer.createTransport({ host: 'smtp.mail-provider.example', port: 587, auth: { user, pass } });
+  await mail.sendMail({ to: customer.email, subject: 'About your rejected return', text });
migrations/0007_customer_tin.sql
+  ALTER TABLE contacts ADD COLUMN taxpayer_id text NOT NULL;   -- copied from efile-gateway, for matching later
src/queue.ts
+  const cached = await redis.get('queue');
+  if (cached) return JSON.parse(cached);
architecture.yaml
+  - external: email-provider
+    purpose: Email customers about their rejection.
```

## What the verdict must say

That all three break a rule, each in its own way: the email goes around the shared notification service (INT-05); the taxpayer identifier isn't needed for contacting anyone (DAT-02); and the cache solves a problem the queue doesn't have (SIM-01). A review that finds one and stops is the failure this sample exists for.
