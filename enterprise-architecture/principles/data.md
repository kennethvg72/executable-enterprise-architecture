# Data (DAT)

NATAX's business is trust with data. The safest data is data that was never collected, and the second safest is data that was never copied.

## Classification

| Class | Meaning | Examples |
|---|---|---|
| **Public** | Meant to be published | Marketing site, published tax guides |
| **Internal** | Not public, low harm if leaked | Internal procedures, aggregate statistics |
| **Confidential** | Harmful to customers or NATAX if leaked | Customer names and contact details, filing status, rejection codes linked to a filing |
| **Taxpayer-Restricted** | Severe harm if leaked; regulated | Taxpayer identification numbers, full tax returns, income and bank details, identity documents |

When data of different classes is combined, the result has the highest class involved.

### DAT-01: Every data store declares its classification
**Rule.** Each data store an application uses (database, bucket, queue, file share, cache) is listed in its `architecture.yaml` with the highest classification of data in it, its system-of-record status and its retention period.
**Why.** You can't protect data you haven't declared. The declaration drives network policy, backup, encryption and access reviews.
**Verified by.** `test`: the pipeline checks the declaration exists. `review`: the Governance Agent checks it is plausible against the schema.

### DAT-02: Collect and copy only what the purpose needs
**Rule.** Applications collect only the data their purpose requires. Taxpayer-Restricted data lives only in its systems of record: returns-service, efile-gateway, customer-idp and payments, as listed in the [landscape](../landscape/landscape.md). Other applications refer to taxpayers and filings by **opaque references** (the filing reference, the customer number) and fetch details through the owning system's API at the moment they are needed, without storing them.
**Why.** Every copy of taxpayer data is a breach waiting to be discovered, and another system to include in every deletion request.
**Verified by.** `review`: the Governance Agent checks schema changes, data flows and API usage. `test`: in applications that aren't systems of record, the Test Agent scans fixtures, logs and database contents produced by the tests for values shaped like taxpayer identifiers. Pattern scanning is a supplementary detector, not proof of absence.

### DAT-03: One system of record per entity
**Rule.** Each business entity (customer, return, filing, payment, rejection) has exactly one system of record, listed in the [landscape](../landscape/landscape.md). Other copies are derived, read-only, declared in `architecture.yaml` and refreshed from the system of record. They are never edited independently.
**Why.** Two systems of record means two truths, and a reconciliation job that nobody owns.
**Verified by.** `review`.

### DAT-04: Non-production environments use synthetic data only
**Rule.** Development, test and acceptance environments use synthetic data, generated by code in the application's repository. Production data, including "masked" or "anonymized" copies, is never copied out of production.
Systems of record need realistic-looking restricted data to test with. Their generators produce it from reserved ranges that can never be real (for example, taxpayer identifiers with a prefix the Tax Authority never issues), so synthetic data is recognizable as synthetic wherever it ends up.
**Why.** Masking fails in practice: free-text fields, rare combinations and joins re-identify people. Synthetic data generators also make tests reproducible, and agents can extend them to cover edge cases that production data doesn't contain yet.
**Verified by.** `test`: non-production databases are network-isolated from production ([SEC-07](security.md#sec-07-test-environments-cant-reach-production)). The pipeline rejects release candidates whose test fixtures aren't produced by a generator in the repository. `review`: the Governance Agent checks that generators don't embed copied data.

### DAT-05: Retention is defined and automated
**Rule.** Every data store has a retention period in `architecture.yaml`, and the application deletes data older than that automatically. Legal holds are the only exception, and they are applied centrally. Audit records ([IAM-07](identity-and-access.md#iam-07-every-action-on-sensitive-data-is-attributable)) are kept for seven years, separately from operational data. Backups expire on their own schedule ([DAT-08](#dat-08-a-backup-isnt-a-backup-until-it-has-been-restored)); after any restore, the application's retention job runs before the data is used again, so deleted data stays deleted.
**Why.** Data kept "just in case" is liability kept just in case.
**Verified by.** `test`: the Test Agent verifies the retention job. `review`.

### DAT-06: PostgreSQL is the database
**Rule.** Operational data goes in PostgreSQL, on a centrally operated cluster. Using any other database requires a decision record showing that PostgreSQL can't meet a stated requirement. The exceptions are platforms that come with their own store, named in the platform's architecture: Dataverse and SharePoint lists for [Power Apps](../../platforms/power-apps/standards.md), the device's encrypted storage for [Android](../../platforms/android/standards.md). Its features (JSONB, full-text search, `LISTEN/NOTIFY`, `SKIP LOCKED` queues, partitioning) are used before adding a separate product for the same job. Files an application owns (uploads, attachments, documents it keeps) are a data store too: declared in `architecture.yaml` as `store: files` with their path, on file storage the [landscape](../landscape/landscape.yaml) declares, with a classification ([DAT-01](#dat-01-every-data-store-declares-its-classification)) and a retention period ([DAT-05](#dat-05-retention-is-defined-and-automated)).
**Why.** One database engine, run well, beats five run adequately (see [SIM-05](simplicity.md#sim-05-one-default-per-need)). PostgreSQL covers the vast majority of NATAX's needs. Files are data like any other: undeclared, they are kept forever, backed up by nobody, and classified by nobody.
**Verified by.** `test`: `architecture.yaml` data stores against the approved list, and file paths against the landscape's file storage.

### DAT-07: Schema changes are versioned and backward compatible
**Rule.** Schema changes are SQL migration files in the application's repository, applied by the pipeline in order. Each migration must be compatible with both the previous and the new version of the application (expand, migrate, then contract in a later release), because both versions run side by side during a rolling deployment across DC1 and DC2.
**Why.** Active/active deployment means there is never a moment when "everything" is on the new version. It also makes rollback possible without restoring a backup.
**Verified by.** `test`: the pipeline runs the previous release's tests against the new schema.

### DAT-08: A backup isn't a backup until it has been restored
**Rule.** Every production data store is backed up automatically, encrypted, to the other datacenter. Backups are immutable for their whole retention period, on storage that neither the pipeline's identities nor any production administrator can delete or shorten. Recovery points are kept for 35 days, plus monthly copies for 13 months. Restores are tested every week ([RES-09](resilience.md#res-09-resilience-is-tested-not-asserted)): a backup is restored into an isolated restore environment that is itself part of production (same controls, no other access, so DAT-04 still holds) and checked by the owning application's verification queries.
**Why.** Replication protects against losing a site. Backups protect against losing data: deletion mistakes, corruption, ransomware. A backup that the attacker, or a broken pipeline, can delete doesn't protect against either. Untested backups don't protect against anything.
**Verified by.** `test`: restore test results are an input to the pipeline. Applications whose last restore test failed can only release fixes.
