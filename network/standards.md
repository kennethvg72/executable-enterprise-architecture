# Zero Trust network standards (ZTN)

These rules add to the central architecture: mainly [SEC-02](../enterprise-architecture/principles/security.md#sec-02-nothing-is-trusted-because-of-where-it-is), [SEC-07](../enterprise-architecture/principles/security.md#sec-07-test-environments-cant-reach-production), [IAM-06](../enterprise-architecture/principles/identity-and-access.md#iam-06-human-administrative-access-is-just-in-time-and-direct), [INT-05](../enterprise-architecture/principles/integration.md#int-05-shared-capabilities-are-used-not-rebuilt), [RES-04](../enterprise-architecture/principles/resilience.md#res-04-three-voting-sites-and-the-witness-is-in-band) and [RES-05](../enterprise-architecture/principles/resilience.md#res-05-one-writer-at-a-time). They never relax them.

### ZTN-01: Policy is generated from intent, never written by hand
**Rule.** Every firewall rule, host ruleset and proxy allowlist is generated by [compile.ts](tools/compile.ts) from `landscape.yaml` and the applications' `architecture.yaml` files. Nobody edits generated files or devices directly.
**Why.** Hand-written rules drift away from what anyone intended, and nobody can say why a rule exists. A generated rule carries its purpose and its source.
**Verified by.** `test`: drift check in [verify.ts](tools/verify.ts) for the repository; daily drift detection on devices ([DEL-04](../enterprise-architecture/principles/delivery.md#del-04-infrastructure-and-network-are-code)).

### ZTN-02: Both sides declare every flow
**Rule.** A flow is allowed only when the consumer declares it in `consumes` and the provider lists the consumer in `provides.consumers`. Zones (staff devices, PAWs, the internet) are declared by the provider. Shared platform flows (logging, secrets, metrics, administration from PAWs) are declared once, centrally, in `platform-flows`.
**Why.** A consumer declaring alone could reach anything. A provider declaring alone accepts traffic nobody explained. Requiring both makes every path a deliberate agreement, with an owner on each end.
**Verified by.** `test`: the compiler refuses one-sided declarations and names the missing approval.

### ZTN-03: Default deny, inbound and outbound, on every host
**Rule.** Every host's ruleset drops everything not explicitly allowed, in both directions, and logs drops at a limited rate. Outbound traffic to the internet goes only through the egress proxy, which allows each service only its declared destinations.
**Why.** Inbound-only filtering stops lateral movement *to* a host, but not *from* a compromised one. Outbound filtering is what stops data from leaving.
**Verified by.** `test`: rendering tests; invariants in verify.ts; probes.

### ZTN-04: Observed traffic is evidence, not permission
**Rule.** Flow logs are used to find out what *happens*. A flow that happens but isn't declared becomes a question for the owners of both ends ([analyze-flows.ts](tools/analyze-flows.ts)), never an automatic addition to the policy. Application owners and the security requirements decide what is legitimate.
**Why.** Generating policy from observed traffic makes today's accidents, workarounds and intrusions permanent.
**Verified by.** `review`: during [rollout](rollout.md), every undeclared flow has a recorded decision.

### ZTN-05: Enforcement in layers, from one source
**Rule.** The same compiled intent is enforced in three places: host firewalls (nftables), HQ's router (traffic to and from HQ, and DC1↔DC2 transit), and the egress proxy. At the application layer, mutual TLS proves which service is calling ([IAM-05](../enterprise-architecture/principles/identity-and-access.md#iam-05-every-workload-has-its-own-identity)).
**Why.** Any single layer can be misconfigured or bypassed. Layers generated from one source can't contradict each other.
**Verified by.** `test`.

### ZTN-06: Tests are deterministic, and there are three kinds
**Rule.**
1. **Invariants** that must hold for any landscape: the internet reaches only the edge; port 22 only from PAWs; database nodes only from load balancers and their own peers; test and acceptance have no paths to production; only the egress proxy reaches the internet; staff devices reach applications only through load balancers; every DC1↔DC2 flow can transit HQ.
2. **Expectations** written by the Test Agent from intent, independently of the compiler ([expectations.yaml](expectations.yaml)). For example: rejection-triage reaches its database, but not other databases, and not the replica in the other datacenter.
3. **Probes**: real connection attempts from representative vantage points, with expected outcomes ([probe.ts](tools/probe.ts)). Positive probes prove legitimate traffic works; negative probes prove everything else is blocked.

Invariants and expectations are checked twice: on the compiled policy, and on the generated rules, read back as text by an evaluator that doesn't use the policy ([nft.ts](tools/nft.ts), [DEL-06](../enterprise-architecture/principles/delivery.md#del-06-checks-verify-the-output-not-the-intent-that-produced-it)). The probe plan is evaluated against the generated rules before a single packet is sent. The two are different kinds of evidence: reading the rules back shows the rules are right; probes corroborate that the network behaves accordingly. A blocked probe whose target answered on another port is consistent with the intended rule, but doesn't prove which device dropped it. Where a probe runner can read the target host's drop counter (the rules log drops with the prefix natax-drop-in), it can attribute the block to that host's policy. A probe run has three outcomes: **pass**, **fail** and **inconclusive**. A blocked probe whose target can't be shown to be up (no other probe reached it) proves nothing, so the run is inconclusive, and an inconclusive run never lets a gate pass.

Running them doesn't require AI. AI helps write policies and tests, investigate findings and propose fixes. The tests establish what actually happens.
**Why.** "We think it's blocked" isn't a security property. And absence of evidence is not evidence of compliance: a probe that timed out because the target was down looks exactly like one the firewall dropped.
**Verified by.** `test`.

### ZTN-07: Probe proportionately
**Rule.**
- **Every change:** invariants and expectations against the compiled policy (seconds), plus targeted probes for the paths the change adds or removes, in test and acceptance.
- **Weekly, and after any change to shared network infrastructure:** the full probe plan from every vantage point in production. Probes only open a TCP connection and close it; they never send application data.
- **Not on every change:** the full regression. A small UI change shouldn't trigger thousands of probes.
**Why.** Fast feedback on each change; full coverage on a schedule.
**Verified by.** `test`: the pipeline records probe runs.

### ZTN-08: When the policy breaks something legitimate, find out which of three things was wrong
**Rule.** When a policy blocks a legitimate dependency, the investigation decides, and records in the affected application's repository, which of these happened:
1. **The implementation was wrong**: the compiler or a renderer has a defect. Fix it and add a test.
2. **The requirements were incomplete**: a manifest didn't declare a real dependency. Declare it, on both sides.
3. **The architecture needs improvement**: the rules made the right thing impossible or too hard. [Escalate](../enterprise-architecture/governance/escalation.md).
**Why.** Each answer has a different fix and a different owner. Without the classification, every outage gets "fixed" by opening the firewall wider.
**Verified by.** `review`.
